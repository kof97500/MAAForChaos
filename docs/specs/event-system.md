# 事件系统设计说明

最后更新：2026-06-09

## 1. 目标

本文档用于定义肉鸽流程中的“事件页系统”设计，解决以下问题：

- 如何识别当前是否为事件页
- 如何读取真实事件名称
- 如何识别事件选项
- 如何判断当前是哪一个事件
- 如何为已知事件做固定决策
- 如何为未收录事件提供通用兜底策略

## 2. 当前已知前提

根据当前观察，事件页具有以下特征：

- 下方存在多个可点击选项框
- 选项框数量不是固定 3 个，而是 `2-4 个`
- 左侧存在一个事件信息按钮
- 点击事件信息按钮后，会展开事件详情区域
- 展开后可以读取真实事件名称
- 每个事件页的选项组合通常比较固定
- 事件决策既可以依赖事件名，也可以依赖选项正文中的高价值文本

其中有一个关键结论：

- 事件信息按钮里的图案不稳定
- 所以不能把图案本身当成事件 ID
- 真正稳定的事件锚点应当是“点击后展示出来的真实事件名称”

## 3. 总体设计

事件系统建议拆成五层。

### 3.1 EventPageDetector

负责：

- 判断当前是否为事件页
- 识别当前事件页大致布局
- 识别当前选项框数量为 `2 / 3 / 4`

输入：

- 当前截图

输出：

- `is_event_page`
- `option_count`
- `option_rects`

### 3.2 EventInfoReader

负责：

- 识别左侧事件信息按钮
- 点击事件信息按钮
- 读取展开后的真实事件名称
- 必要时读取事件副标题或人物名

输入：

- 当前事件页截图

输出：

- `event_name`
- `event_subtitle`
- `detail_opened`

说明：

- 真实事件名称应作为事件识别主键的第一候选
- 如果事件详情打开失败，才回退到只靠选项标题/正文匹配

### 3.3 EventOptionExtractor

负责：

- 针对每个选项框裁切区域
- 提取标题文本
- 提取说明文本
- 尽量抽取关键收益/代价词

输入：

- 当前截图
- 选项框区域列表

输出：

- 每个选项的结构化信息

示例：

```json
[
  {
    "index": 1,
    "title": "献上赞美",
    "description": "信用点增加100，普通战斗3次期间异形生命值变为1"
  },
  {
    "index": 2,
    "title": "洗清罪孽",
    "description": "移除所选1张卡牌"
  },
  {
    "index": 3,
    "title": "打破平静",
    "description": "所有主战员压力增加20，选中主战员闪光1次"
  }
]
```

### 3.4 EventMatcher

负责：

- 根据真实事件名称、选项标题组合识别事件
- 命中事件配置表中的已知事件

输入：

- `event_name`
- 当前事件页提取出的选项信息

输出：

- `event_id`
- `matched`
- `confidence`

### 3.5 EventDecisionPolicy

负责：

- 按正文高优先级规则优先选择
- 对已知事件走固定选择
- 对未知事件走通用兜底逻辑

输入：

- `event_name`
- `event_id`
- 当前选项列表

输出：

- 应点击的选项序号
- 决策原因

## 4. 第一版推荐识别流程

建议第一版事件处理使用下面这条顺序：

1. 判断当前是否为事件页
2. 识别当前有几个选项框
3. 点击左侧事件信息按钮
4. 读取真实事件名称
5. 提取每个选项的标题和正文
6. 先跑正文高优先级规则
7. 再跑事件名称匹配
8. 最后才走未知事件兜底策略

这样做的好处是：

- 事件识别主锚点更稳定
- 同名事件的决策更容易配置
- 文本高价值规则也能覆盖事件默认选择

## 5. 事件页识别

第一版可以先结合布局规则判断：

- 页面主体为事件人物/插画
- 下方存在 `2-4` 个规则排列的选项框
- 页面中央存在对白/标题文本区域
- 左侧存在事件信息按钮区域

如果这几个条件成立，就判定为 `事件页`。

## 6. 选项框识别

因为选项数量为 `2-4` 个，不能把坐标完全写死成 3 框模式。

建议第一版做成：

- 先识别底部选项框整体区域
- 再按横向分布检测框数量
- 生成 `option_rects`

如果短期内不同事件页布局高度一致，也可以先做一个保守版本：

- 预设 `2` 框布局
- 预设 `3` 框布局
- 预设 `4` 框布局
- 运行时根据边框/间距匹配最接近的布局

## 7. 已知事件决策

已知事件建议优先采用“事件配置表 + 文本高优先级规则”驱动。

也就是说，对已知事件：

- 允许某段正文强命中时直接优先选择
- 否则按事件名称命中的规则选
- 再次才按标题组合作辅助匹配

### 7.1 建议的数据结构

```json
{
  "event_id": "messenger_of_girken",
  "event_names": [
    "基尔肯的传令兵"
  ],
  "match_mode": "event_name_and_option_titles",
  "options": [
    "献上赞美",
    "洗清罪孽",
    "打破平静"
  ],
  "preferred_choice": 1,
  "reason": "默认优先拿普通战斗异形生命值变为1"
}
```

说明：

- `event_names` 用于真实事件名称匹配
- `options` 用于辅助确认
- `preferred_choice` 是默认点击序号
- 序号从 `1` 开始，和左到右一致

### 7.2 匹配方式建议

第一步优先用：

- 真实事件名称完全匹配
- 或真实事件名称关键词匹配

第二步再用：

- 选项标题完全匹配
- 或选项标题关键词匹配

原因：

- 真实事件名称更适合作为事件主键
- 选项标题适合作为辅助确认
- 比单纯依赖正文更稳定

## 8. 文本高优先级规则

除了 `event_id -> preferred_choice` 这一层，还需要支持：

- 不管当前事件名称是什么
- 只要某个选项正文命中某段高价值文本
- 就优先选择该项

### 8.1 适用场景

例如：

- `普通战斗3次期间异形生命值变为1`
- `获得装备`
- `获得传说卡牌`

这类文本本身就足以说明该选项具有较高价值，应该允许它覆盖默认事件规则。

### 8.2 建议优先级

事件决策推荐使用以下优先级：

1. 正文强优先规则
2. 事件名称专属固定规则
3. 事件名称 + 选项标题组合规则
4. 未知事件关键词打分
5. 默认位置兜底

### 8.3 建议的数据结构

```json
{
  "priority_text_rules": [
    {
      "match_text": "普通战斗3次期间异形生命值变为1",
      "action": "prefer",
      "reason": "高价值战斗收益"
    }
  ]
}
```

## 9. 未收录事件的通用兜底逻辑

这部分非常重要，因为肉鸽中一定会逐步遇到新事件。

如果当前事件没有命中配置表，不应该直接卡死，而应该进入兜底决策。

### 9.1 兜底目标

- 尽量保守
- 尽量避免高风险负面项
- 尽量优先明确收益项
- 即使不能最优，也要保证流程继续

### 9.2 兜底规则建议

可以按关键词做一个简单打分。

#### 加分关键词

- `获得`
- `回复`
- `恢复`
- `增加`
- `提升`
- `装备`
- `遗物`
- `卡牌`
- `祝福`
- `稀有`
- `传说`

#### 减分关键词

- `减少`
- `失去`
- `扣除`
- `随机失去`
- `最大生命值减少`
- `承受`
- `痛苦`
- `无法`
- `负面`
- `诅咒`

### 9.3 兜底决策流程

建议按这个顺序：

1. 先检查是否命中文本高优先级规则
2. 再检查是否命中事件名称规则
3. 对每个选项做关键词打分
4. 优先选择得分最高项
5. 如果多个得分接近，优先选较“中性”的项
6. 如果完全无法判断，走默认顺序

### 9.4 最终默认顺序

当 OCR、关键词、事件匹配都不可靠时，建议留一个最后兜底顺序，例如：

- 对于 `2` 选项：`[1, 2]`
- 对于 `3` 选项：`[2, 1, 3]`
- 对于 `4` 选项：`[2, 3, 1, 4]`

这个顺序不是“最优”，但通常比盲点边缘选项更稳。

## 11. 与状态机的关系

事件系统不应该直接塞进主状态机里写死，而应该作为状态机中的一个子模块。

建议后续这样接：

- 状态机识别到 `事件页`
- 调用 `EventPageDetector`
- 调用 `EventInfoReader`
- 调用 `EventOptionExtractor`
- 调用 `EventMatcher`
- 调用 `EventDecisionPolicy`
- 返回要点击的选项
- 状态机执行点击并等待结果页

也就是说：

- 状态机负责调度
- 事件系统负责识别和决策

## 12. 第一版实现顺序建议

建议按下面的顺序做。

### 阶段 1：事件页识别

目标：

- 能稳定判断“当前是事件页”
- 能检测当前有几个选项框

### 阶段 2：事件名称读取

目标：

- 能识别并点击左侧事件信息按钮
- 能拿到真实事件名称

### 阶段 3：选项区裁切

目标：

- 稳定得到 `2-4` 个选项框区域

### 阶段 4：选项标题提取

目标：

- 拿到每个选项的标题
- 描述提取可以放在第二优先级

### 阶段 5：事件配置表匹配

目标：

- 已知事件优先按真实事件名称匹配
- 已知事件走固定规则

### 阶段 6：未知事件兜底决策

目标：

- 配置表未命中时仍能继续流程

## 13. 当前结论

事件页是肉鸽阶段非常适合优先策略化的一类页面，因为：

- 页面结构相对稳定
- 选项数量有限
- 左侧详情按钮能提供更稳定的真实事件名称
- 选项正文里也可能出现高价值强规则文本

因此第一版最推荐的路线是：

1. 先把 `2-4` 选项事件页识别出来
2. 点击左侧按钮读取真实事件名称
3. 用事件名称和选项标题匹配已知事件
4. 用事件配置表做固定选择
5. 对未收录事件增加关键词兜底逻辑
6. 对高价值正文规则允许覆盖默认事件选择

这条路线能在较低复杂度下，尽快做出一个足够可用的事件系统。
