# 卡厄思梦境 PC 自动化开发计划

最后更新：2026-06-08

## 1. 项目目标

构建一个运行在 `Windows` 上、面向 `卡厄思梦境 PC 客户端` 的原生自动化工具，能够稳定完成以下流程：

- 启动或连接游戏窗口
- 进入肉鸽模式
- 以保守规则完成第一层
- 领取第一层奖励
- 安全结束本局或重新开始下一轮

本项目明确采用 `黑盒视觉自动化` 路线：

- 通过截图识别当前游戏画面
- 通过规则与任务流做决策
- 通过鼠标键盘模拟执行操作
- 不进行内存修改、协议篡改、代码注入等行为

## 2. 成功标准

第一阶段里程碑达成的标准如下：

- 能在 Windows 上以固定支持分辨率运行
- 能稳定连接到 PC 客户端窗口
- 在常见简单场景下，无需人工干预完成“第一层奖励”流程
- 在识别失败时，能通过重试或安全退出恢复
- 能生成日志与失败截图，便于后续调试

第一阶段的非目标：

- 自动通完整个肉鸽
- 构筑优化
- 复杂事件收益评估
- 多角色最优策略
- 高胜率智能 AI
- 反作弊绕过相关工作

## 3. 产品范围

### V1 范围内

- Windows 原生窗口控制
- 固定分辨率支持
- 仅支持“肉鸽第一层奖励”刷取
- 仅支持一个指定角色/起手流派
- 基础战斗规则
- 基础事件/奖励选择规则
- 重试、超时、失败日志

### V1 范围外

- 手机模拟器支持
- 初版即支持多分辨率
- 通用于所有游戏模式
- 复杂构筑策略
- 大量依赖 OCR 识别全部卡牌名
- 后台多任务与产品级体验打磨
- 面向公开发布的安装包完善

## 4. 技术方向

### 主路线

- `MaaFramework`：自动化运行时与任务编排框架
- `Win32 Controller`：PC 客户端窗口截图与输入控制
- `Python Agent`：承载自定义识别与动作逻辑
- `OpenCV`：模板匹配、区域分析、简单图像判断
- `OCR`：仅在必须识别文本时使用

### 选择原因

- 游戏存在原生 Windows PC 客户端，`Win32` 比 `ADB` 更适合。
- 当前目标范围较窄，基于规则的方案比复杂决策引擎更快落地。
- MaaFramework 已经提供了控制器、Pipeline、自定义识别器与动作模块等关键抽象。

### 备选路线

如果官方 PC 客户端对 Win32 输入兼容性不佳，则退一步采用：

- 仅支持前台运行
- 降低点击频率，使用更保守的操作节奏
- 要求运行期间游戏窗口保持焦点

如果 MaaFramework 早期接入受阻，则可以先做临时 PoC：

- Python
- Win32 直接截图/输入
- OpenCV
- OCR

即便使用临时 PoC，也应保持同样的状态机设计，后续再迁回 MaaFramework。

## 5. 核心系统设计

系统拆分为以下模块。

### 5.1 控制层

职责：

- 查找或连接游戏窗口
- 校验支持的分辨率
- 采集窗口截图
- 发送鼠标点击、移动、滚轮与键盘输入

输出：

- 控制器配置
- 窗口绑定规则
- 支持的分辨率列表

### 5.2 识别层

职责：

- 判断当前所处界面状态
- 识别按钮、战斗状态、奖励界面、弹窗
- 检测当前流程是否正常推进

识别方式：

- 模板匹配：用于稳定按钮与图标
- 固定区域颜色/形状检测：用于简单状态判断
- OCR：仅在无法规避文本识别时使用

### 5.3 决策层

职责：

- 选择下一步执行任务
- 在战斗中按简单规则出牌
- 决定何时结束回合
- 决定何时放弃并重开

V1 决策风格：

- 仅采用保守启发式规则
- 不做搜索树
- 不做训练模型

### 5.4 Pipeline / 状态机层

职责：

- 驱动端到端流程
- 管理重试、超时、分支与恢复
- 将战斗逻辑与非战斗逻辑分离

### 5.5 日志与调试层

职责：

- 输出结构化运行日志
- 在失败步骤保存截图
- 记录状态切换耗时
- 生成简单调试材料，便于复现问题

## 6. 里程碑

### 里程碑 0：项目初始化

目标：

- 建立仓库结构与基础文档

交付物：

- 文档索引
- 开发计划
- 初始目录结构
- 决策记录模板

退出标准：

- 仓库已具备继续进行技术验证的基础

### 里程碑 1：技术可行性验证

目标：

- 证明 Windows PC 客户端可被稳定控制

任务：

- 确认游戏可在固定支持分辨率下运行
- 验证可从游戏窗口稳定截图
- 测试多种 Win32 输入方式
- 验证对几个稳定 UI 目标的点击准确性
- 记录截图与点击延迟

交付物：

- 可行性验证报告
- 确认的窗口模式与分辨率
- 最终选定的截图/输入方案

退出标准：

- 至少有一种截图方式与一种输入方式在目标机器上稳定可用

### 里程碑 2：外层流程自动化

目标：

- 自动完成进入第一层前的非战斗流程

任务：

- 从标题页或主菜单连接进入
- 进入肉鸽模式
- 开始新局
- 处理固定确认框与简单选择项

交付物：

- 游戏外层导航 Pipeline
- 菜单与按钮模板资源
- 菜单跳转失败后的重试规则

退出标准：

- 工具无需人工操作即可到达第一场战斗或第一层可玩状态

### 里程碑 3：战斗 MVP

目标：

- 通过简单规则完成第一层中的常见简单战斗

任务：

- 识别“玩家回合”
- 识别可操作手牌或可出牌位置
- 识别可攻击目标区域
- 识别“结束回合”按钮
- 实现保守的出牌顺序规则

示例规则：

- 优先打明显可用的低费牌
- 在局面简单时，优先使用直接伤害牌
- 当识别置信度不足时，提前结束回合，避免误操作

交付物：

- 战斗自定义识别器与动作模块
- 战斗规则说明文档
- 多组第一层战斗测试截图

退出标准：

- 在常见简单战斗中，能以可接受稳定性完成第一层战斗

### 里程碑 4：第一层奖励闭环

目标：

- 端到端完成“第一层奖励”刷取循环

任务：

- 识别战斗胜利
- 自动处理战后奖励流程
- 完成奖励领取
- 根据配置退出本局或重新开始

交付物：

- 第一版完整刷取闭环
- 奖励与退出界面的失败处理逻辑

退出标准：

- 工具可重复完成第一层奖励循环，并提供日志与失败恢复能力

### 里程碑 5：稳定性加固

目标：

- 提高可用性与可维护性

任务：

- 降低识别误判
- 调整超时与恢复策略
- 增加更多战斗样本
- 文档化常见失败模式
- 规划基础 Windows 打包方案

交付物：

- 稳定性检查清单
- 已知问题文档
- 打包计划

退出标准：

- 项目已稳定到可供个人持续使用

## 9. 风险清单

### 技术风险

- Win32 输入兼容性可能受游戏客户端实现方式影响。
- 窗口特效、缩放、过场动画可能降低模板稳定性。
- 即便只是第一层，战斗随机性也可能暴露简单规则的不足。
- 如果字体样式或特效复杂，OCR 稳定性可能不如预期。

### 产品风险

- 即使目标范围很窄，也可能需要在版本更新后频繁维护。
- 错误点击可能导致跑图失败或奖励损失。

### 合规风险

- 即便是黑盒视觉自动化，也仍可能违反游戏规则或服务条款。

## 12. 待验证问题

以下问题应在技术验证阶段优先回答：

- 哪个固定分辨率最稳定？
- 游戏是否接受后台输入，还是必须保持前台聚焦？
- 哪种 Win32 截图方式最稳定？
- 战斗决策是否必须依赖 OCR，还是 V1 可以主要依靠模板与区域判断？
- 哪个角色或初始流派最适合做第一层刷取？
